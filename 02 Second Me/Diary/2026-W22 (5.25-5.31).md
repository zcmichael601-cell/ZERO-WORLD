### LLM 是如何训练的？

数据来源：万亿 Token（网页 / 书籍 / 代码）

1. **预训练 Pre-training** → 基座模型
   预测下一个 token，`Loss = -log P(tokenN+1 | t1...tN)`。把人类文字规律压缩进参数，但不懂听指令。

2. **监督微调 SFT** → 指令模型
   在 (问题, 高质量回答) 标注对上训练，只计算回答部分的损失。教模型对话格式和风格。

3. **强化学习 RLHF / DPO** → 对齐模型（GPT-4 / Claude / Gemini）
   - RLHF：人工标注偏好 → 训练奖励模型 RM → PPO 最大化分数（KL 惩罚防漂移）
   - DPO：直接在 (好回答, 差回答) 对上优化，省掉奖励模型

4. **推理训练 Reasoning RL** → 推理模型（o1 / R1）
   答对 +1 答错 0，模型在 `<think>` 里自由打草稿，自己学会了 Chain-of-Thought。

每一层都在解决上一层解决不了的问题，推理模型是目前的终点，但不是终点。

| 阶段 | 核心问题 | 信号来源 |
|------|----------|----------|
| 预训练 | 语言是什么规律？ | 文本自身（无监督） |
| SFT | 怎么按要求回答？ | 人工标注的好答案 |
| RLHF/DPO | 哪个回答更好？ | 人工的偏好比较 |
| 推理训练 | 怎么把问题想清楚？ | 答案对错（自动验证） |

### LLM 相比之前的增量价值？

LLM 的核心优势在于文本理解与生成、代码辅助、知识问答、多步推理、复杂指令跟随、意图理解和 plan，在"语言密集型任务"上表现突出。

AI 之前就存在的场景，LLM 只是提升了效率：搜索、翻译、规则型客服、基础代码补全。

真正的增量场景——AI 之前几乎不可能实现的：

1. 普通人能编程：自然语言描述需求就能得到可用代码，技能门槛消失。
2. 零样本跨域知识融合：把法律、医学、用户具体情况同时推理，之前需要专家团队。
3. 非结构化文档理解：上传合同、财报、论文直接提问，之前需要人工阅读或专用系统。
4. Agent 自主任务链：给一个目标，AI 自主拆解步骤、调用工具、执行反馈，之前必须硬编码流程。
5. 个性化教育辅导：根据学生具体错误实时调整解释，之前只有昂贵家教能做到。
6. 创意与人类协同生成：头脑风暴、初稿、风格模仿，之前创意工作完全依赖人类。

判断框架：凡是过去需要"雇一个聪明的人类专家才能完成的语言密集型任务"，LLM 大概率是真增量。凡是只需要确定性规则、精确计算、实时数据，LLM 相对传统方案优势有限。

### 如何挑选模型？
  场景                     推荐模型          原因
  ---------------------------------------------------------
  意图分类 + 槽位提取      小模型/规则       结构化任务，<100ms，成本极低
  追问生成                 中等模型（Flash）  需要自然语言能力，但复杂度不高
  推荐文案生成             中等模型（Flash）  创意 + 格式，主力场景
  对比分析                 中等或大模型       多维推理，准确性要求高
  LLM-as-Judge（评测）     大模型            评测质量要求高，非实时

  导购系统里，意图分类完全可以用规则 + 小模型解决，不需要调用
  GLM-4-Flash。把贵的模型留给真正需要生成能力的步骤。

### 如何评测效果？
  Layer 0：模型能力层（Model-level）
    └── NLP 基础能力：意图识别、槽位提取、文本相关性、幻觉率
    └── 不依赖线上流量，纯离线可跑

  Layer 1：系统质量层（System-level）
    └── 链路整体效果：检索召回质量、排序质量、生成质量
    └── 离线评测为主，部分指标需要人工标注

  Layer 2：用户体验层（Experience-level）
    └── 用户感知质量：交互自然度、推荐可信度、决策帮助度
    └── 人工评测 + LLM-as-Judge 为主

  Layer 3：业务结果层（Business-level）
    └── 最终商业指标：CTR、CVR、GMV、留存率
    └── 只能在线评测（A/B 实验）

  设计要点：
  - Golden set：人工标注的黄金测试集，固定不变，用于跨版本横向对比
  - Shadow eval：线上流量同时跑旧版+新版，对比diff
  - LLM-as-judge：用强模型对输出打分，降低人工成本

  1. 评测体系本身也要迭代：如果你的 eval 不随业务演进，Golden set 会腐化，指标会失真
  2. 人在回路不能省：全自动迭代在早期很容易出现"指标好看但用户体验变差"的 Goodhart's Law陷阱，每个关键节点要有人工 sanity check

#### 分析与归因（找到真正的问题）：
  - 向量聚类：对失败 case 做 embedding 聚类，发现系统性缺陷
  - 错误分类：把失败按根因分桶（知识缺失 / 推理错误 / 格式问题 / 指令遵循）
  - 变化追踪：每次 deploy 自动对比 eval diff，定位变更引入的 regression

#### 迭代决策层（闭环的核心）：
  根据分析结果，自动触发不同的迭代路径：
  评测结果
      │
      ├─ 数据问题 ──→ 自动挖掘/标注更多训练数据
      │
      ├─ Prompt 问题 ──→ 自动 Prompt 优化（DSPy/APE）
      │
      ├─ 模型问题 ──→ 触发 Fine-tuning pipeline
      │
      ├─ 流程问题 ──→ 更新 workflow/工具调用逻辑
      │
      └─ 产品设计问题 ──→ 转人工 backlog

  关键：设置决策阈值和人工审核门禁
  - 低风险变更（如 prompt 微调）可全自动上线
  - 高风险变更（如模型替换）必须人工确认


### 上下文和提示词如何设计
先用一句话区分：
  ▎ 提示词工程 = 怎么"问"得好=角色（你是谁+语气）+rules（问题+目标+指令+约束）+output Format（输出结构）
 一个好的 Prompt 由三段组成：Role 定义身份（"你是谁"），Rules 约束行为（"你要做什么、不能做什么"），Output
  Format 锁死输出格式。Agent 的判断逻辑和异常处理指令全写在 Rules 里，不写在 Role
  里——判断标准是：去掉这句话，是 Agent
  的"身份"变了还是"行为"变了。格式约束要用明确的禁止规则，比"尽量""请注意"这类软性描述有效得多。在此基础上加
  Few-shot 示例，是锁定输出格式最强的手段：给 2-3 个覆盖边界情况的"输入→输出"例子，放在 Rules
  之后、当前请求之前，LLM 会直接从示例里学到模式，比文字描述规则更稳定。示例的格式必须和目标输出完全一致，不
  能有任何差异，否则会污染模式。以追问场景为例，三个示例分别覆盖"零槽位/部分槽位/槽位快满"三种状态，LLM
  就能同时学到追问的格式要求和槽位优先级，一个示例做两件事。

  ## Few-shot 输出格式控制

  ### Few-shot 示例怎么设计
  关键技巧：
  - 示例要覆盖边界情况（零槽位 / 部分槽位 / 接近完整）
  - 示例的输出格式要和目标格式完全一致，不能有任何差异
  - 2-3 个精选示例比 10 个平庸示例效果更好

  原则一：覆盖边界情况，而不是只给"正常情况"
  ❌ 三个示例都是"正常流程"：
    示例1：槽位完整 → 推荐
    示例2：槽位完整 → 推荐
    示例3：槽位完整 → 推荐

  ✓ 覆盖不同状态：
    示例1：零槽位 → 追问（边界：什么都不知道时怎么做）
    示例2：部分槽位 → 追问（主流程）
    示例3：槽位快满了 → 追问最后一个（边界：快完成时怎么做）

  原则二：示例的输入输出格式，必须和真实请求完全一致
  ❌ 示例里的格式和真实请求格式不一样：
  示例输出：
    question: 是送给谁的
    choices: 妈妈/爸爸/朋友

  真实请求期望格式：
    {"question": "...", "options": [...]}

  → LLM 会混淆，有时输出 choices，有时输出 options

  ✓ 完全一致，示例就用目标格式：
  示例输出：{"question": "是送给谁的？", "options": ["妈妈", "爸爸", "朋友"]}
  真实期望：{"question": "...", "options": [...]}

  原则三：示例之间要有"递进关系"，演示推理过程
  示例1：槽位为空 → 问最优先的槽位（recipient）
  示例2：有 recipient → 问次优先的槽位（price）
  示例3：有 recipient + price → 问第三优先的槽位（preference）

  → LLM 从示例里学到了槽位追问的优先级顺序：
    recipient > price > category > preference
    不需要你在规则里再写一遍

  ▎ 上下文工程 = 怎么把"背景信息"塞得好=背景+对话
    上下文工程的核心是：按"变化频率"分层，只把必要的层送入每次请求。固定的系统 Prompt
  放最外层，对话历史做滑动窗口（保留最近 6 轮），槽位和意图用结构化字段而非原始对话传递，RAG
  检索结果只送摘要不送全文。以导购系统为例，把"帮我给妈妈买护肤品，不要含酒精的，玫瑰香型，预算 300
  以内"这段对话历史替换成结构化槽位 {recipient:妈妈, category:护肤品, price_max:300, exclude:含酒精, 
  preference:玫瑰香型}，token 从约 100 压缩到约 50，LLM 对结构化字段的遵从率还更高。商品 Context
  同理，每个商品只送标题、核心卖点和评价摘要（约 50 token），而不是详情页全文（约 500 token），10
  个候选商品的 Context 成本从 5000 token 降到 500 token。在此之上，用模型分级进一步降本：意图分类走规则或小模
  型，追问和推荐生成走中等模型，只有评测或复杂推理才用大模型；高频相似请求（槽位组合相同的导购）走缓存，缓存
  key 是槽位 hash 而非原始文本，头部场景命中率可达 30-40%。整体策略：先做 Prompt 结构保质量，再做 Context
  压缩降成本，最后做缓存做极致优化。

### 如何优化效果和成本？
降低成本的方法

  1. 减少 Token 用量（最直接）

  Prompt 压缩
  - 去掉冗余措辞、例子精简化
  - 用结构化格式（JSON schema）替代自然语言描述
  - 工具：LLMLingua、Selective Context

  输出长度控制
  # 明确限制输出格式
  "用不超过3句话回答，只返回JSON，不要解释"

  上下文窗口管理
  - 滑动窗口：只保留最近 N 轮对话
  - 摘要压缩：把历史对话压缩成摘要再传入

   缓存相似请求（最容易被忽视的降本点）
  # 缓存 key = 意图类型 + 槽位 hash（不是原始文本）
  cache_key = hash(f"{intent.type}:{sorted(slots.items())}")

  # 命中率估算：
  # 同类礼品导购（recipient=妈妈, category=护肤, price=100-300）
  # 这类"相似槽位"的请求量很大，缓存 TTL=1小时 可覆盖 30-40% 流量

  注意：缓存的是"槽位相同的推荐结果"，不是"输入文本相同"。后者命中率极低，前者在头部场景命中率可以很高。

  ---
  2. 用更便宜的模型（性价比核心）
  
  分级路由（Model Routing）
  简单任务 → 小模型（Haiku、GPT-4o-mini）
  复杂任务 → 大模型（Opus、GPT-4o）

  判断路由的方式：任务复杂度分类器、置信度阈值、规则匹配。

  Speculative Decoding（推测解码）
  - 小模型草稿 → 大模型验证，吞吐量提升 2-4x，成本不变但速度快

  ---
  3. 缓存（避免重复计算）

  KV Cache / Prompt Cache
  - Claude、GPT-4o 均支持前缀缓存
  - 固定的 system prompt、few-shot examples 只计算一次
  - 命中缓存的 token 折扣可达 50-90%

  system prompt（固定）→ 缓存
  + user message（变化）→ 只算增量

  语义缓存
  - 相似问题复用历史回答（GPTCache、Redis + embedding 相似度）

  ---
  4. 批处理（提升吞吐降低单价）
  
  - Anthropic / OpenAI 的 Batch API 成本直降 50%
  - 适合离线任务：数据标注、批量摘要、评估

  ---
  5. 自部署开源模型（彻底去掉 API 费用）

  ┌────────────────┬───────────────────────────┐
  │      场景      │           方案            │
  ├────────────────┼───────────────────────────┤
  │ 高并发固定任务 │ Llama 3 / Qwen2.5 + vLLM  │
  ├────────────────┼───────────────────────────┤
  │ 端侧/边缘      │ Gemma 2B、Phi-3 量化版    │
  ├────────────────┼───────────────────────────┤
  │ 微调专用场景   │ LoRA 微调小模型替代大模型 │
  └────────────────┴───────────────────────────┘

  自部署的隐形成本：GPU 租用、运维、模型维护，需综合算 TCO。

  ---
  决策框架

  任务量小 / 原型阶段   → 直接用 API，不优化
  任务量中等           → Prompt 压缩 + 模型路由 + Prompt Cache
  任务量大 / 成本敏感   → Batch API + 语义缓存 + 考虑自部署
  固定垂直场景         → 微调小模型，长期最优

  核心原则：先量化（算清楚每个任务花多少），再优化（找最大的浪费点），而不是无差别压缩所有 token。


## 05/27 周三
AI幻觉，主要是来源于预训练数据中本来就不存在/存在但不正确/存在且正确，但是总结错误or丢失；
AI时代产品经理的核心逻辑没有变，还是理解用户、定义问题、解决方案和推动落地。只是1）系统确定性变了，从确定性系统编程了不确定性的系统，要有评测、实验、迭代和兜底意识；2）for human/agent的交互方式变了；3）Demo输出更提效了；

  1. 训练阶段
  - RLHF / RLAIF：用人类或 AI 反馈强化真实性偏好
  - 事实增强预训练：混入高质量知识密集型语料
  - 对比解码（Contrastive Decoding）：抑制低质量子模型的输出概率

  2. 推理阶段（最实用）
  - RAG（检索增强生成）：让模型"带着资料回答"，把知识外置到可验证的数据库
  - Chain-of-Thought + 自我核查：让模型先推理再验证，或多次采样取一致答案
  - 不确定性感知：置信度低时让模型说"我不知道"而非强行回答
  - 低温采样：降低 temperature 减少随机性（代价是多样性下降）

  3. 后处理阶段
  - 事实核查管道：用独立模型或搜索引擎验证生成内容
  - 引用溯源：强制模型给出来源，无来源则拒绝
