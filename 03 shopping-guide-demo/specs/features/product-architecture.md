## 一、用户场景

> **调研依据**：本章节结合客户调研报告（`strategy/customer.md`）和竞品调研报告（`strategy/competitive.md`）结论进行设计，调研结论标注 ▶ 符号。

### 1.0 用户画像（调研支撑）

**▶ 目标用户与购物主力人群高度重合，无需另找细分**

AI 电商核心用户集中在 **25-44 岁（占比 83.1%）**，与现有电商平台高频购物用户完全重叠（头豹研究院，2025）。冷启动策略：优先让平台内最活跃的现有用户先用起来，而非拓展新人群。

**▶ AI 渗透率已过临界点，不需要教育用户**

2025 年中国生成式 AI 普及率已达 **36.5%**（净增 106.6%，CNNIC），用户知道如何与 AI 交互。产品的主要挑战不是「教会用户」，而是「第一次用就体验好，让用户回来」——准确率和稳定性优先于新手引导设计。

**▶ 移动化完成，碎片场景是主战场**

手机网民占比 99.7%，用户在小屏幕、碎片化时间下完成购物决策，「快速给出答案」的价值远大于「功能完整」。

| 用户类型 | 规模信号 | 核心痛点 | 对我们的设计要求 |
|---------|---------|---------|----------------|
| **需求模糊型** | 搜索行为从品牌词向泛需求演变（CBNData，2024） | 说不清楚要买什么，传统搜索框无法接收 | 追问要像朋友聊天，每次只问一个问题 |
| **选择困难型** | 用户平均跨 4.5 个平台比价（+42% YoY） | 各平台结果不可信，不知道该信哪个 | 给推荐理由 + 无广告标注，让用户在一个平台就能决策 |
| **效率优先型** | 明确知道要买什么，不需要 AI 介入 | 被 AI 拦截追问，反而变慢 | 明确需求直接走传统链路，不触发追问 |
| **研究型买家** | 大额商品调研时间长（3C/家电） | 参数看不懂，跨品牌对比太累 | Help Me Decide + 人话参数解释 |
| **隐私敏感型** | 37.6% 用户因隐私顾虑减少使用 AI 功能 | 不知道数据被怎么用 | 主动说明数据用途，不留存搜索记录 |

### 1.1 导购场景

**核心定位**：用户有购物意图但需求不明确，系统通过追问澄清后给出精准推荐。

**▶ 调研结论：这是 AI 导购的最大机会场景**

传统关键词搜索对模糊 Query 处理能力极弱。用户「给 8 岁爱运动的孩子推荐生日礼物」这类自然语言，传统搜索只能拿到「运动 礼物 8岁」关键词组合，体验差距巨大。Help Me Decide 类功能是「传统搜索最无力」× 「用户最需要帮助」的黄金交叉点（CBNData 泛需求演变趋势）。

**▶ 竞品对标：Amazon Rufus 是最强参照**

Rufus 对话导购带来 **60% 转化率提升**、$120 亿增量销售；阿里「一句话购物」累计近 2 亿次。行业追问体验的通病：**追问流程生硬，用户不知道要提供什么信息**（竞品调研普遍痛点），这是我们的差异化机会。

| 子场景 | 典型输入 | 用户心理 | 链路策略 | 设计重点 |
|-------|---------|---------|---------|---------|
| **礼品导购** | "帮我找个母亲节礼物" | 不知道买什么，希望被引导 | LLM 追问（recipient→price→preference）→ 推荐 | 追问像朋友聊天，提供快捷选项卡 |
| **场景匹配** | "给 10 岁爱运动的孩子买生日礼物" | 有场景有对象，需要匹配 | LLM 槽位追问（品类+预算）→ 推荐 | 槽位提取要准确识别「10岁」「爱运动」 |
| **预算导购** | "300 块以内买个好耳机" | 明确预算上限，要最优解 | 传统搜索（价格过滤）+ LLM 推荐排序 | 推荐理由要体现「这个价位最值」 |
| **品类探索** | "最近有什么好用的护肤品" | 无明确商品，想发现新品 | 推荐链路 + 热榜 + LLM 推荐文案 | 结果要有「为什么推荐这个」的说明 |
| **研究型导购** | "帮我选一台家用洗碗机，我家 4 口人" | 大额商品，怕选错 | LLM 多维追问（装修风格/预算/关注点）→ 对比推荐 | Help Me Decide 是核心，人话解释差异 |
| **选择困难** | "这两款空气炸锅哪个适合我" | 有候选，不知怎么决策 | LLM 对比分析（竞品 comparison 功能） | 对比维度要贴近用户需求，不堆参数 |
| **追问中断恢复** | 用户追问到一半，隔天回来继续 | 之前说了一半，不想重复 | Session 上下文持久化，自动带入历史槽位 | 「你上次说是送给妈妈的，预算确认下？」 |

**▶ 追问体验是决定留存的关键（竞品调研）**

行业通病是「追问生硬，像填表单」。追问设计原则：① 每次只问一个问题；② 提供 3-5 个快捷选项；③ 最多追问 3 轮；④ 追问文案口语化、个性化（不复读已知信息）。

### 1.2 搜索场景

**核心定位**：用户有明确商品目标，快速定位，AI 不介入。

**▶ 调研结论：解决「跨平台搜索跳出」比解决「搜索失败」更有价值**

用户平均同时使用 **4.5 个平台**进行搜索（较 2022 年+42%），根本原因是单平台结果让人「不够有信心做决策」（customer.md 启示三）。传统搜索的核心机会不是提高召回率，而是**让结果足够可信，用户不需要去别处验证**——即推荐理由 + 无广告透明度。

**▶ 62.32% 的用户首要诉求是「广告少/体验好」**（艾媒咨询，2025）

这是传统搜索差异化的核心：明确标注无广告、结果排序逻辑透明。

| 子场景 | 典型输入 | 用户心理 | 链路策略 | 设计重点 |
|-------|---------|---------|---------|---------|
| **精确搜索** | "Nike Air Max 42 码黑色" | 我就要这个，别拦我 | 传统链路，<200ms | 不触发追问，直接出结果 |
| **品牌词搜索** | "苹果手机 128G" | 品牌已定，找规格 | 传统链路 + 属性过滤 | 规格过滤要精准 |
| **型号搜索** | "iPhone 15 Pro Max" | 精确型号，找价格/库存 | 传统链路精准匹配 | 价格排序 + 正品标注 |
| **跨平台比价搜索** | "这款耳机哪里最便宜" | 不信任单一结果，要比价 | 传统链路 + 价格排序 + AI 简短说明 | AI 说明「这是平台内最低价，无广告」建立信任 |
| **纠错搜索** | "爱疯15"（拼音/错别字）| 懒得打正确，希望系统懂 | QP 纠错 → 传统链路 | 纠错后提示「为你搜索：iPhone 15」 |
| **零结果搜索** | 长尾 / 过于细化的词 | 找不到，很沮丧 | 传统链路零结果 → 兜底 + 建议改词 | 「没找到，试试这些相关词：…」 |

**▶ 搜索后 AI 介入时机**

明确搜索成功（≥3 个结果）：不介入，保持速度优势。搜索结果 1-2 个：触发 LLM 补充推荐，悄悄增强，不打断用户。搜索零结果：触发兜底 + AI 引导换词。

### 1.3 推荐场景

**核心定位**：用户未主动搜索，系统基于上下文或行为主动推荐。

**▶ 调研结论：推荐准确率需 >85% 才能真正改变用户习惯**（竞品调研普遍痛点）

行业大多数系统准确率在 70-80%，用户「试一次不准，就不再用」。首要目标是提高准确率，而非功能覆盖广度。

**▶ 个性化推荐是核心竞争力，但隐私是真实门槛**

37.6% 的用户因隐私顾虑减少使用 AI 功能（南方都市报，2025）。推荐策略：短期基于当前 Session 内上下文推荐（不需要历史数据，隐私风险极低），中长期引入可控的个性化（用户明确授权）。

| 子场景 | 触发时机 | 推荐逻辑 | 展示位置 | 设计重点 |
|-------|---------|---------|---------|---------|
| **首页发现** | 用户进入 App | 今日热销榜（全站 + 品类）+ Session 内上下文（后续迭代加个性化） | 发现页 | 热榜有更新时间标注，增加可信度 |
| **对话内补充推荐** | 传统搜索结果 1-2 个时 | LLM 基于槽位补充推荐，不打断搜索结果 | 对话消息流，在搜索结果下方 | 标注「AI 为你补充推荐」，区分来源 |
| **Help Me Decide 触发** | 用户在搜索结果页犹豫（滚动≥3次，无点击） | LLM 主动介入，生成对比摘要 | 对话悬浮入口 | 主动但不打扰，用户可关闭 |
| **购后关联推荐** | 用户查看商品详情页 | 配件 / 同款不同规格 / 同品类热销 | 商品详情页底部 | 推荐理由要关联已选商品（「配合你看的这款…」） |
| **兜底热销推荐** | 任何链路失败时 | 品类热销 Top-10（预缓存，每小时刷新） | 对话消息流 | 标注「今日热销」，不假装是个性化推荐 |
| **跨品类联想推荐** | 用户搜索完成后，有关联购买意图 | 基于当前品类的常见搭配（电脑→鼠标；护肤→防晒） | 对话消息流，用户点击后触发 | 「买了这个的人还常买…」，需用户主动点击，不主动推送 |

### 1.4 竞品对标场景（设计参照）

基于竞品调研，以下功能/场景是行业验证有效的，纳入设计参考：

| 竞品 | 参照功能 | 效果数据 | 我们的对应设计 |
|-----|---------|---------|-------------|
| **Amazon Rufus** | 对话式导购（Help Me Decide） | 转化率提升 60%，月活+140% | 核心链路对标，追问自然度是超越点 |
| **Amazon Rufus** | 嵌入原生 App 而非独立 App | 用户习惯门槛低，更易触达 | 对话导购作为现有 App 的能力升级，不做独立入口 |
| **阿里千问** | 一句话购物（完整闭环） | 累计近 2 亿次 | 搜索→推荐→下单不跳转，闭环优先 |
| **Google AI Mode** | Query Fan-out（多角度理解需求） | AI 出现在 14% 购物搜索 | QP 层多路 Query 改写，覆盖用户意图的多种表达 |

**▶ 竞品普遍痛点 → 我们的差异化方向**

| 行业通病 | 我们的策略 |
|---------|----------|
| 推荐混入广告，用户不信任 | 明确标注「无广告推荐」，结果排序逻辑对用户透明 |
| 追问生硬像填表单 | 每次只问一个问题 + 快捷选项卡 + 口语化文案 |
| 通用品类浅，垂直深度不足 | 优先选 1-2 个垂直品类做深（3C / 家居），而非做全品类 |
| AI 推荐公信力低于真人评测 | 推荐理由引用真实用户评价摘要，让「AI 说的」有出处 |
| 需要跳转多个平台比价 | 一个对话内给出推荐理由 + 无广告标注，让用户不需要去验证 |

### 1.5 场景优先级（基于调研）

**▶ 调研结论排序：优先解决「选择困难 + 需求模糊」，而非「搜索失败」**

| 优先级 | 场景 | 调研依据 | 目标指标 |
|-------|------|---------|---------|
| **P0** | 需求模糊导购（追问+推荐） | 搜索从品牌词向泛需求演变；Rufus 60% 转化提升 | 追问接受率 >70%；推荐 CTR >50% |
| **P0** | 选择困难（Help Me Decide） | 用户跨 4.5 平台比价；竞品调研的差异化机会 | 对话完成率 >80% |
| **P1** | 精确搜索（快速响应） | 效率优先用户需求；62% 用户要求广告少 | P95 <200ms；无广告感知 |
| **P1** | 隐私透明（数据用途说明） | 37.6% 用户因隐私减少使用 | 隐私说明曝光率 100%（首次对话） |
| **P2** | 首页热销推荐 | 用户进入 App 的冷启动体验 | 点击率 >20% |
| **P2** | 跨品类联想推荐 | 购后关联，提升 LTV | 后续版本迭代 |
| **P3** | 虚拟试用 / 拍照搜品 | 竞品已做，技术复杂度高 | v2.0 规划 |

## 二、用户核心流程

> 本章从 **C 端用户视角** 描述每个核心功能的页面交互流程：用户在哪个页面、看到什么、做了什么操作、页面如何响应。系统内部链路（Router、QP、LLM 调用等）不在本节体现，详见第五章算法设计。

### 2.1 导购场景用户流程（P0）

```
[首页]
用户看到对话框 + 快捷话题入口
（帮我找礼物 / 推荐手机 / 今天最火…）
      │
      ▼
用户点击快捷话题 或 直接输入模糊需求
（例：「帮我找个母亲节礼物」）
      │
      ▼
[对话页] 页面进入对话视图，消息流出现 AI 追问气泡
      │
      ▼
─────────────────────────────────────────────
需求是否已足够明确？
      │
      ├── 是 ──────────────────────────────────────────────→ [见 ★ 推荐结果]
      │
      └── 否 → AI 展示追问气泡（每次只问 1 个问题 + 快捷选项卡）
                    ┌────────────────────────────┐
                    │ 🤖 是送给谁的？             │
                    │  [妈妈] [朋友] [同事] [另一半] │
                    └────────────────────────────┘
                        │
                        ▼
              用户点击选项 或 自由输入回答
                        │
                        ▼
              对话继续，追问气泡消失，已选信息显示在消息流中
                        │
                        ▼
              已追问 3 轮？
                ├── 否 → 还有关键信息缺失 → 继续追问
                └── 是 → 进入推荐（即使信息不完整）
─────────────────────────────────────────────
      │
      ▼
[对话页] ★ 推荐结果区域出现（流式逐字展示 AI 文案）
      │
      ▼
展示 2-4 张商品卡片，每张包含：
  · 商品图片 + 名称 + 价格
  · 1-2 句个性化推荐理由（体验描述，非参数堆砌）
      │
      ▼
─────────────────────────────────────────────
商品数量 ≥ 3 个？
  ├── 是 → 卡片下方出现「怎么选？」Help Me Decide 区域
  │           A 款：…  B 款：…  C 款：…
  └── 否 → 仅展示商品卡片
─────────────────────────────────────────────
      │
      ▼
用户操作分支：
  ① 点击商品卡片 → [商品详情页]
  ② 点击「换个推荐」→ 对话继续，AI 重新推荐
  ③ 点击 👎 → 弹出原因选项（太贵 / 不准 / 理由不够…）→ AI 重新推荐
  ④ 在输入框继续追问（「有没有便宜一点的？」）→ 对话继续
      │
      ▼
[商品详情页]
  · 基础信息（图片 / 名称 / 价格 / 评分）
  · AI 为你说（结合本次对话需求的个性化说明）
  · 用户评价摘要
      │
      ▼
用户点击「立即购买 / 加入购物车」→ 跳转购买链路
```

```
      │
      ▼
[搜索结果页] 展示商品列表
      │

  ├── ≥ 3 个 → 正常展示商品列表（按相关性排序）
  │             页面顶部可见筛选栏（价格 / 品牌 / 好评率…）

  │
  ├── 1-2 个 → 展示有限结果
  │             列表底部安静出现「AI 为你补充推荐」区域
  │             （不打断主结果，不强制引导）
  │
  └── 0 个   → 空状态页面：
                「没找到，试试这些词：…」
                [相关词建议 1]  [相关词建议 2]  [相关词建议 3]
─────────────────────────────────────────────
      │
      ▼
用户操作分支：
  ① 点击商品 → [商品详情页]
  ② 点击筛选条件 → 列表实时刷新
  ③ 点击纠错提示中的词 → 以新词重新搜索
  ④ 点击改词建议 → 以建议词重新搜索
      │
      ▼
[商品详情页]
用户决策 → 购买 / 继续浏览
```

### 2.3 推荐/发现场景用户流程（P2）

```
[首页/发现页]（用户进入 App，未主动搜索）
      │
      ▼
页面展示：
  · 今日热销榜（含更新时间标注，增加可信度）
  · 各品类快速入口（3C / 家居 / 护肤…）
  · 对话入口（主入口，始终可见）
      │
      ▼
用户操作分支 A — 主动点击：
  ① 点击热销商品 → [商品详情页]
```

### 5.2 传统搜推链路

#### 5.2.1 QP（Query Processing）

| 模块 | 功能 | 输出 | 延迟目标 |
|-----|------|------|---------|
| **分词 & 纠错** | 分词（jieba/自研）、拼写纠错 | token[] | <10ms |
| **同义词扩展** | 品牌别名、规格同义词（"苹果"→"Apple"） | synonym_tokens[] | <5ms |
| **Query 改写** | 生成多路 Query（精确/宽泛/同义） | query_variants[] | <20ms |
| **意图分类** | 识别 intent.type / clarity / complexity | intent{} | <50ms |
| **槽位提取** | 结构化参数抽取（category/price/brand…） | slots{} | <30ms |

#### 5.2.2 索引与召回

| 召回路径 | 技术方案 | 适用场景 | 召回量 |
|---------|---------|---------|-------|
| **倒排索引** | Elasticsearch / 自研倒排 | 精确关键词匹配 | Top-100 |
| **向量召回** | FAISS / Milvus，Embedding 模型 | 语义相关商品 | Top-50 |
| **属性过滤** | 品类/价格/品牌结构化过滤 | 附加条件精确筛选 | 叠加在上述两路 |
| **热销兜底** | 预计算品类热销 Top-100，缓存 | 冷启动 / 关键词无匹配 | Top-10 |

**多路召回合并策略：**
```
merged_candidates = deduplicate(
    倒排召回 × 0.6 + 向量召回 × 0.4
)
→ 进入粗排，候选集 ≤ 200
```

#### 5.2.3 特征与排序模型

**粗排（Coarse Ranking）**

| 特征类型 | 特征示例 | 模型 |
|---------|---------|------|
| 相关性特征 | BM25 得分、向量相似度 | 线性模型 / LightGBM |
| 商品质量特征 | 评分、销量、好评率 | 同上 |
| Query-商品交叉 | 关键词命中率、品类匹配 | 同上 |

目标：200 个候选 → 50 个进入精排，延迟 <30ms

**精排（Fine Ranking）**

| 特征类型 | 特征示例 | 模型 |
|---------|---------|------|
| 用户特征 | 历史品类偏好、价格带偏好 | DNN / GBDT |
| 商品特征 | 点击率、转化率、曝光率 | 同上 |
| 上下文特征 | 当前 Session 内已看商品、已点击商品 | 同上 |
| 交叉特征 | 用户×商品历史交互、实时行为 | 同上 |

目标：50 个候选 → Top-20，延迟 <50ms

**综合得分公式（精排）：**
```
score = w1 × relevance + w2 × quality + w3 × ctr_pred + w4 × cvr_pred
      = 0.3 × relevance + 0.2 × quality + 0.3 × ctr_pred + 0.2 × cvr_pred
```

#### 5.2.4 重排与 SLA

**重排（Re-ranking）**

```
精排 Top-20 → 重排层
    ├── 去重（同款不同 SKU 合并）
    ├── 多样性保障（同品牌商品数 ≤ 3）
    ├── 业务干预注入（干预层，见第 13 节）
    ├── SLA 保障检查（库存 / 价格有效性）
    └── 最终输出 Top-10（传统链路）
```

**传统链路 SLA：**

| 指标 | P50 | P95 | P99 |
|------|-----|-----|-----|
| QP 耗时 | <50ms | <100ms | <150ms |
| 召回耗时 | <30ms | <80ms | <120ms |
| 粗排耗时 | <15ms | <30ms | <50ms |
| 精排耗时 | <30ms | <50ms | <80ms |
| 重排耗时 | <10ms | <20ms | <30ms |
| **端到端总时延** | **<100ms** | **<200ms** | **<300ms** |
| 可用性 | - | - | >99.9% |

### 5.3 LLM 导购链路

#### 5.3.1 索引（向量知识库）

| 索引类型 | 内容 | 更新频率 | 用途 |
|---------|------|---------|------|
| **商品向量索引** | 商品标题 + 详情 Embedding | 实时增量（新品上架时） | RAG 检索候选商品 |
| **评价摘要索引** | 用户评价聚类摘要 Embedding | T+1 | 提供真实用户视角 |
| **Q&A 索引** | 商品详情问答 Embedding | T+1 | 处理 detail_inquiry |
| **热榜索引** | 品类热销预计算，KV 缓存 | 每小时刷新 | 兜底补充 |

**检索策略：**
```
Query Embedding → ANN 检索（FAISS）
→ 召回 Top-20
→ 按品类/价格槽位过滤
→ 最终 Context Top-10（送入 Prompt）
```

#### 5.3.2 上下文管理（Context）

```
Context 构成（按优先级）：
┌────────────────────────────────────────────┐
│ [System Prompt]        ← 角色 / 规则 / 格式│
│ [对话历史]（最近 6 轮） ← 多轮理解上下文   │
│ [当前意图 & 槽位]      ← 结构化用户需求    │
│ [检索到的商品]（Top-10）← RAG 候选结果    │
│ [用户输入]             ← 当前 Turn 输入   │
└────────────────────────────────────────────┘

Context 长度控制：
- 对话历史：保留最近 6 轮，超出滑动窗口截断
- 商品 Context：每个商品最多 200 token（标题+核心属性+评价摘要）
- 总 Token 上限：4000 tokens（含输入输出预留）
```

#### 5.3.3 Prompt 设计

**追问 Prompt（Clarification）：**
```
System:
你是一个专业的购物助手。用户需求还不够清晰，你需要追问一个最关键的缺失信息。
规则：
1. 每次只问一个问题
2. 追问用自然口语，像朋友聊天，不像填表格
3. 提供 3-5 个快捷选项（中文，短语形式）
4. 不要重复已知信息

输出格式：JSON
{"question": "追问文案", "options": ["选项1", "选项2", ...]}

User:
当前已知槽位：{slots}
对话历史：{history}
用户最新输入：{user_input}
最关键缺失槽位：{missing_slot}
```

**推荐 Prompt（Recommendation）：**
```
System:
你是一个专业无广告的购物推荐助手。根据用户需求和检索结果，推荐最合适的 2-4 个商品。
规则：
1. 推荐理由必须和用户的具体需求挂钩
2. 用体验描述，不用参数（"一天不用充电"而非"5000mAh"）
3. 每个推荐理由最多 2 句话
4. 如果返回 ≥3 个，生成 Help Me Decide 对比摘要

输出格式：JSON
{
  "reply": "推荐文案（100字以内）",
  "products": [{"id": "...", "reason": "推荐理由"}],
  "help_me_decide": "对比摘要（可选）"
}

User:
用户需求槽位：{slots}
候选商品列表：{retrieved_products}
对话历史：{history}
```

**对比 Prompt（Comparison）：**
```
System:
用户想对比几个商品，用人话解释核心差异，并给出适合该用户的建议。
规则：不要用"产品A/产品B"，用商品实际名称。核心差异用 2-3 个维度。

输出格式：JSON
{
  "comparison": [{"dimension": "维度", "analysis": "对比说明"}],
  "recommendation": "基于用户需求的建议"
}
```

#### 5.3.4 LLM 大模型选型

| 指标 | GLM-4-Flash（首选） | Claude Haiku（备用） |
|-----|-------------------|-------------------|
| 延迟（首字） | <800ms | <1s |
| 成本 | 低（约 0.1元/千tokens） | 中 |
| 中文能力 | 强 | 中 |
| API 稳定性 | 国内直连 | 需代理 |
| 适用场景 | 追问 / 推荐生成 | 临时备用 |

**大模型调用策略：**
```
主模型：GLM-4-Flash
    → 超时（>5s）或错误率 >5% → 切换备用模型
    → 备用模型也失败 → 进入兜底链路

流式输出：Server-Sent Events (SSE)
    → 首 token 到达立即推送前端
    → 完成后一次性渲染商品卡片
```

#### 5.3.5 LLM 链路 SLA

| 指标 | 目标值 | 超限处理 |
|------|-------|---------|
| 流式首字时延 | <1s | 超 2s 展示 loading 动画 |
| P95 完整响应 | <3s | 超 5s 触发超时降级 |
| LLM 调用成功率 | >95% | 低于 90% 自动切主备 |
| 端到端可用性 | >99.5% | 兜底链路兜底 |
| 单次 Token 成本 | <0.05元 | 超限触发 Prompt 压缩 |

### 5.4 兜底链路

**触发条件（任一满足）：**

| 触发场景 | 条件 | 优先级 |
|---------|------|-------|
| LLM 服务异常 | 超时 >5s 或 HTTP 5xx | 最高 |
| 传统搜索零结果 | product_count == 0 | 高 |
| 意图置信度低 | confidence < 0.5 | 中 |
| 追问超限 | session.turns > 3 且 clarity == unclear | 中 |
| 搜索服务异常 | ES 不可用 | 最高 |

**兜底逻辑：**
```
① 提取已有品类槽位
   有品类 → 该品类热销 Top-10（缓存，每小时刷新）
   无品类 → 全站今日热销 Top-10

② 生成兜底文案（规则模板，不调 LLM）
   LLM_TIMEOUT   → "稍等，给你看看今天卖得最好的…"
   ZERO_RESULT   → "没找到完全匹配的，这些相关商品供你参考…"
   LOW_CONFIDENCE → "我先给你看看大家都在买什么…"

③ 引导语
   "告诉我更多信息（预算/场景），我帮你精准推荐"
```

**兜底链路 SLA：**

| 指标 | 目标值 |
|------|-------|
| P95 响应时延 | <100ms（全走缓存） |
| 可用性 | >99.99%（最后防线，不依赖外部服务） |

### 5.5 降级链路

降级是一种**主动的、分级的服务降质**策略，区别于兜底（被动触发）。

**降级等级定义：**

| 等级 | 触发条件 | 降级策略 | 恢复条件 |
|-----|---------|---------|---------|
| **L0（正常）** | 所有服务健康 | 全链路正常 | - |
| **L1（轻度降级）** | LLM 调用延迟 P95 >3s | 关闭 Help Me Decide；推荐理由简化 | LLM P95 <2s 持续 5min |
| **L2（中度降级）** | LLM 成功率 <90% | 所有请求走传统链路；LLM 仅用于追问 | 成功率 >95% 持续 10min |
| **L3（重度降级）** | LLM 成功率 <70% 或搜索异常 | 全部走兜底热销，关闭 AI 功能 | 人工审核后恢复 |

**降级配置（Feature Flag）：**
```yaml
degradation:
  level: 0                    # 当前等级（0-3）
  llm_enabled: true           # LLM 功能总开关
  help_me_decide_enabled: true
  streaming_enabled: true
  max_recommend_count: 4      # 降级时减少为 2
  llm_timeout_ms: 5000        # 降级时缩短为 3000
```

**自动降级触发逻辑（监控联动）：**
```python
if llm_p95_latency > 3000ms for 2min:
    set_degradation_level(L1)
if llm_success_rate < 0.90 for 1min:
    set_degradation_level(L2)
if llm_success_rate < 0.70 for 30s:
    set_degradation_level(L3)
    alert("LLM 链路严重故障，已自动降级到 L3")
```

```
└── 大模型输出质量评测
    ├── 自动评测（LLM-as-Judge）
    │   ├── 相关性（1-5分）
    │   ├── 理由质量（是否匹配槽位）
    │   └── 安全性（无广告/无偏见）
    └── 人工评测（周期性抽样）
        ├── 每周抽取 100 条对话
        └── 标注：好/中/差 + 原因
```

### 6.2 评测数据集

| 数据集 | 规模 | 构建方式 | 更新频率 |
|-------|------|---------|---------|
| 意图分类标注集 | 1000 条 | 人工标注 | 季度更新 |
| 槽位提取标注集 | 500 条 | 人工标注 | 季度更新 |
| 推荐质量标注集 | 200 条 / 周 | 人工 + LLM Judge | 周更新 |
| A/B 实验基准集 | 线上流量分桶 | 自动采集 | 实时 |
| Badcase 集合 | 动态增长 | 用户反馈 + 人工审核 | 实时 |

### 6.3 核心评测指标

| 指标 | 计算方式 | 目标值 | 报警阈值 |
|------|---------|-------|---------|
| 意图识别准确率 | 正确识别数 / 总数 | >85% | <75% |
| 槽位 F1 | 精确率×召回率 调和均值 | >0.8 | <0.7 |
| 对话完成率 | 看到推荐的会话 / 总会话 | >80% | <60% |
| 推荐 CTR | 点击商品数 / 展示商品数 | >50% | <30% |
| 推荐质量（人工）| 好评率 | >70% | <50% |
| LLM 链路成功率 | 成功调用 / 总调用 | >95% | <90% |

## 八、Badcase 管理

### 8.1 Badcase 分类

| 类型 | 定义 | 来源 | 严重程度 |
|-----|------|------|---------|
| **意图误判** | 系统把明确搜索当导购（或反之） | 用户反馈 / 人工标注 | 高 |
| **推荐无关** | 推荐商品与用户需求不相关 | 用户反馈 | 高 |
| **槽位遗漏** | 关键槽位未提取（漏掉价格/受众） | 人工标注 | 中 |
| **追问不当** | 追问了不必要的问题 / 重复追问 | 用户反馈 | 中 |
| **推荐理由差** | 理由通用、不匹配槽位 | 人工评测 | 中 |
| **时延超标** | 响应时间超过 SLA 目标 | 监控日志 | 中 |
| **LLM 幻觉** | 推荐了不存在的商品 / 编造评价 | 人工审核 | 高 |
| **安全问题** | 出现广告植入 / 歧视性内容 | 人工审核 | 最高 |

### 8.2 Badcase 处理流程

```
Badcase 发现
    │
    ▼
打标分类（自动 + 人工）
    │
    ▼
根因分析
    ├── 意图/槽位模型问题 → 更新训练数据 → 重新训练 → 评测
    ├── Prompt 问题 → 修改 Prompt → A/B 验证
    ├── 检索问题 → 检查索引数据 / 改写策略
    └── 数据问题 → 清洗商品数据
    │
    ▼
制定修复方案（产出工单）
    │
    ▼
修复实施 → 回归测试
    │
    ▼
验证：该 Badcase 不再复现 → 关闭
    │
    ▼
沉淀到训练集（防止同类问题再现）
```

### 8.3 Badcase 积累策略

- 每周产出 Badcase 报告（按类型 / 严重程度分布）
- 连续 2 周同类 Badcase >10 条 → 必须排期修复
- Badcase 数据集版本化管理，与模型版本关联

## 十、自进化

自进化是系统持续优化的闭环机制，将线上数据、用户反馈转化为模型和策略迭代。

### 10.1 问题归因

```
数据输入：
├── 用户 👎 反馈（附原因）
├── Badcase 库（已打标）
├── 日志分析结论
├── A/B 实验失败组分析
└── 监控告警触发记录

归因分析流程：
    数据聚合 → 按类型/场景分类
         │
         ▼
    根因定位
    ├── 是 Prompt 问题？（LLM 输出测试）
    ├── 是模型问题？（离线评测对比）
    ├── 是数据问题？（商品库 / 评价数据质量）
    ├── 是策略问题？（Router 逻辑 / 权重）
    └── 是工程问题？（缓存 / 索引更新延迟）
         │
         ▼
    输出归因报告 → 进入迭代设计
```

### 10.2 迭代设计

| 迭代类型 | 周期 | 产出物 | 审批机制 |
|---------|------|-------|---------|
| **Prompt 优化** | 随时 | 新 Prompt 版本 | 小实验验证后上线 |
| **模型更新** | 月度 | 新模型权重 | 离线评测达标 → 灰度 → 推全 |
| **策略调整** | 双周 | 路由规则 / 权重变更 | A/B 实验验证 |
| **数据优化** | 周度 | 训练集更新 / 数据清洗 | QA 验收 |
| **大版本重构** | 季度 | 架构/算法升级 | PM + Tech Lead 审批 |

### 10.3 A/B 实验

**实验框架：**
```
实验设计
├── 实验假设（假设 Prompt 优化能提升推荐 CTR 5%）
├── 实验单元（用户级 / 请求级）
├── 流量分配（对照组 50% / 实验组 50%）
├── 实验周期（最少 7 天，统计显著性）
└── 成功指标（CTR / 完成率 / 满意率）

实验类型：
├── Prompt 实验（不同版本 Prompt 对比）
├── 模型实验（旧模型 vs 新模型）
├── 策略实验（Router 权重 / 阈值调整）
└── UI 实验（商品卡片布局 / 追问文案）
```

**流量分层（防实验干扰）：**
```
Layer 1：核心链路实验
Layer 2：Prompt 实验
Layer 3：UI 实验
同层实验互斥，不同层实验可并行。
```

### 10.4 评测（迭代内）

每次迭代上线前必须通过：

| 检查项 | 方式 | 通过标准 |
|-------|------|---------|
| 意图准确率不退步 | 离线评测集 | ≥ 基线 -1% |
| 时延不退步 | 性能基准测试 | P95 ≤ 基线 +20ms |
| Badcase 不新增 | Badcase 回归 | 已知 Badcase 全部通过 |
| LLM 输出质量 | LLM-as-Judge 抽样 | 质量评分 ≥ 基线 |

### 10.5 推全策略

```
灰度阶段：
├── 内部用户（白名单） → 验证无崩溃
├── 5% 流量 → 观察 24h，对比指标
├── 20% 流量 → 观察 48h
└── 100% 推全

推全熔断机制：
    任何阶段，若核心指标（CTR / 完成率）下降 >10%
    → 自动停止灰度 → 触发告警 → 人工审核
```

## 十二、自回滚

### 12.1 自动回滚触发条件

| 触发场景 | 判断逻辑 | 回滚目标 |
|---------|---------|---------|
| 上线后成功率骤降 | 成功率对比发布前下降 >15% | 回滚到上一个版本 |
| 时延急剧恶化 | P95 超 500ms 持续 3min | 回滚到上一个版本 |
| 错误率激增 | 错误率 >5% 持续 2min | 回滚到上一个版本 |
| 核心指标下降 | CTR / 完成率下降 >20% 持续 10min | 暂停灰度并告警 |

### 12.2 回滚策略

```
回滚类型：
├── Prompt 回滚：配置化管理，秒级生效，无需重新部署
├── Feature Flag 回滚：关闭功能开关，秒级生效
├── 模型版本回滚：切换模型端点，分钟级生效
└── 代码版本回滚：触发 CI/CD 回滚 Pipeline，5-10 分钟

自动回滚流程：
    监控检测异常
        │
        ▼
    等待确认（30 秒，给人工窗口介入）
        │
        ▼
    自动执行回滚（优先最轻量的方式）
        │
        ▼
    发送告警通知（说明回滚原因 + 回滚版本）
        │
        ▼
    人工确认回滚完成 + 分析根因
```

### 12.3 回滚保障

- 所有 Prompt 版本化存储，支持一键切换
- 模型权重保留最近 3 个版本
- 代码发布支持蓝绿部署，回滚无停机
- 回滚后强制走 Badcase 回归测试，确认问题消除

## 十三、干预

干预是**人工或规则对算法结果的主动调整**，用于处理算法自身无法解决的场景。

### 13.1 干预类型

| 类型 | 场景 | 干预方式 | 作用范围 |
|-----|------|---------|---------|
| **商品屏蔽** | 问题商品（假货/违规）需要下架 | 黑名单屏蔽 | 搜索 + 推荐 |
| **商品置顶** | 运营活动商品需要提升曝光 | 权重加权 / 强制插位 | 特定 Query 或场景 |
| **Query 映射** | 特定词汇需要重定向（"苹果手机"→品类页） | Query 改写规则 | 传统链路 QP |
| **Prompt 补丁** | 特定意图需要特殊处理逻辑 | Prompt 条件注入 | LLM 链路 |
| **兜底内容干预** | 特定活动期间兜底展示活动商品 | 替换热销榜 | 兜底链路 |

### 13.2 干预管理后台

```
干预规则结构：
├── rule_id
├── type（block / boost / redirect / prompt_patch）
├── condition（query_match / category / time_range）
├── action（具体干预参数）
├── priority（多规则冲突时的优先级）
├── effective_time（生效时间段）
├── creator / approver
└── status（active / paused / expired）
```

**干预优先级：**
```
商品屏蔽（最高）> 置顶插位 > 权重加权 > Query 改写 > 正常算法结果
```

### 13.3 干预审批流

```
运营提出干预需求
    │
    ▼
填写干预规则（后台表单）
    │
    ▼
算法评审（影响面评估）
    │
    ▼
PM 审批（P0/P1 级干预需 PM 批准）
    │
    ▼
干预上线（配置下发，秒级生效）
    │
    ▼
效果观察（关注 CTR / 完成率变化）
    │
    ▼
到期自动关闭 / 人工续期
```

## 十四、成本优化

### 14.1 成本构成

| 成本项 | 估算（Demo 阶段） | 主要驱动因素 |
|-------|----------------|------------|
| LLM API（GLM-4-Flash） | ¥5-20 / 天 | 调用次数 × 平均 Token 数 |
| 向量检索（FAISS 自建） | 极低（内存） | 索引大小 |
| 搜索服务（ES） | 按需（云服务） | 索引文档数 × QPS |
| 服务器（Python FastAPI） | ¥30-100 / 月 | 实例规格 |

### 14.2 LLM 成本优化策略

| 策略 | 方案 | 预期降本 |
|-----|------|---------|
| **Prompt 压缩** | 精简 System Prompt，移除冗余描述 | 10-20% |
| **Context 窗口控制** | 对话历史最多 6 轮，商品摘要 200 token | 20-30% |
| **缓存相似 Query** | 对高频 Query（意图+槽位相同）缓存 LLM 结果 | 15-25% |
| **模型分级调用** | 简单追问用小模型；复杂推荐用大模型 | 20-40% |
| **流量降级** | L2 降级后 LLM 只处理追问，推荐走传统链路 | 50%+ |
| **Batch 处理** | 非实时日志分析 / 评测用 Batch API（低成本） | 仅评测场景 |

### 14.3 成本监控

```
实时监控：
├── 每小时 LLM Token 消耗
├── 每日成本累计（与预算对比）
└── 每次请求平均成本趋势

告警阈值：
├── 日成本 >预算 120% → Slack 通知
├── 日成本 >预算 150% → 自动触发 L2 降级（减少 LLM 调用）
└── 单次请求 Token >3000 → 告警 + Prompt 压缩检查

成本优化目标（v1.0）：
├── LLM 链路平均成本 <¥0.03 / 次
└── 月度 LLM 总成本 <¥500
```
