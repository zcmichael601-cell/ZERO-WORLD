### 3. 多 Agent 扩展：内部子 Agent 与外部 Agent

补充日期：2026-10-08。架构图 01 与调用关系图 02A 已将本节能力纳入；02B 继续展开模型、Memory 与 RAG 的基础依赖，图 03 保留单 Agent 选购基线。本节是按需启用的目标设计，不表示当前 Demo 已实现子任务调度、外部 Agent 接入或持久恢复。

**结论：默认用 App 确定性流程或“单 Agent + 多 Tool”；当任务可拆成边界清晰、需要各自探索的子问题，且收益经评测能够覆盖协调成本时，再启用“主 Agent + 受控子 Agent”。跨部门或合作方已有独立 Agent 时，经 Agent Gateway 按最小授权委派，不把所有服务都改名为 Agent。**

#### 3.1 先区分四种容易混淆的能力

| 形态 | 能力与调用方式 | 本方案定位 |
| --- | --- | --- |
| Skill | SOP、Prompt、允许工具与输出契约；由 Runtime 装配执行 | 一组方法，不是一个必然拥有独立循环的 Agent；同一 Agent 可以使用多个 Skill |
| 普通 Tool / Domain | 输入确定参数，返回候选、价格、证据或排名；RPC / API / MCP 适配 | 优先复用确定性业务能力；并行调用多个 Tool 不等于多 Agent |
| 内部子 Agent | 独立 childRun、受限上下文、专用 Skill / Prompt、模型调用和工具循环，返回子任务产物 | 主 Runtime 经委派管理器启动；可同进程、同池 Worker 或独立工作池，不要求一角色一服务 |
| 外部 Agent | 不归当前 Runtime 直接管理循环、状态和发布的独立执行方，通常有 ownTaskId 与独立鉴权 | 可以是集团内其他部门、独立平台或第三方；经 Agent Gateway 接入，信任边界不能因“内部团队”而省略 |

外部 Agent 的“外部”是**运行与权限边界之外**，不只指公网。模型服务、天气 API、普通搜索 API 并不会因为跨网络就成为外部 Agent。相反，内部子 Agent 也可以独立部署；区分依据是生命周期与执行责任，而不是进程或机器位置。

#### 3.2 多 Agent 的优势，以及成立条件

| 潜在优势 | 本项目可得到的收益 | 成立条件与代价 |
| --- | --- | --- |
| 独立分支并行探索 | 不同品类、不同证据来源、不同备选方案可同时研究，减少串行等待 | 分支必须低耦合；总时延还包括拆分、最慢分支、汇总和复核，不保证更快；总 Token 通常增加 |
| 专业能力与上下文隔离 | 专门的商品证据、套装兼容性、出游规划 Agent 使用不同 Skill、工具和证据窗口 | 需有真实专业任务，而非给相同 Prompt 换三个角色名；摘要压缩可能丢细节，必须保留可回读证据 |
| 能力复用与独立迭代 | 复用其他部门已有的专业 Agent，供多个场景按契约调用 | 需要稳定接口、权限、SLA、版本兼容、Owner 与故障降级；普通 API 足够时不增加 Agent 协议 |
| 有界复核与风险识别 | 对复杂比较追加“验证约束 / 查冲突证据”子任务，减少遗漏 | 相同模型共享错误来源，多个 Agent 同意不等于事实正确；最终要查权威事实，不靠投票取代核验 |
| 故障隔离与部分交付 | 可选分支失败时保留可靠主结果，并说明缺失部分 | 隔离来自运行时设计，不是多 Agent 自动提供；必需分支失败不能被多数成功掩盖 |

成本判断采用同一批请求对比：单 Agent + 粗粒度工具、单 Agent + 并行工具、多 Agent 三种方案，比较约束满足、证据忠实、P95 完成时延、每个有效任务成本和失败恢复。不要把行业研究任务的收益比例直接套用到购物请求。〔M1、M2〕

#### 3.3 什么时候启用：先过门槛，再选模式

启用前应同时满足：①子问题可定义独立目标、输入和验收产物；②子问题本身需要多步动态判断，而非一次 API；③可将上下文和权限裁剪到最小；④可分配全局预算内的子预算与截止时间；⑤有合并冲突和部分失败策略。并行只有在依赖满足后才开始，不能在候选 SKU 未确定时“同时研究这几款商品”。

| 业务请求 | 推荐模式 | 为什么 |
| --- | --- | --- |
| 关键词搜索、筛选、推荐刷新、查库存、读一份说明书 | App → Domain 或单 Agent + Tool | 目标确定、调用简单，不需要额外模型循环 |
| 500 元内比较 3 款通勤耳机，资料已齐全 | 单 Agent + 并行只读 Tool（默认） | 先搜候选，再并行核价与检索证据；已有工具足以解决，不能为了展示架构强拆 Agent |
| 多品牌家电“整套购置”，不同品类需要多步比较 | 主 Agent + 品类子 Agent（按需并行） | 主任务分配子预算 / 候选配额，各分支研究后统一做总预算、兼容与配送校验；子任务各自合格不代表组合合格 |
| 多款商品的规格、测评与评价冲突，需阅读大量材料 | 主 Agent + 证据研究子 Agent / 有界验证子 Agent | 隔离长上下文和探索；返回支持、反证、缺失项和原文引用，主任务不按多数意见裁决 |
| 北京出游 + 装备选购，复用独立旅行团队的行程能力 | 主 Agent + 内部选购子 Agent + 外部旅行 Agent | 只有行程确需自主规划时才委派；若只查天气 / 景点仍用 Tool。先共享必要日期、地点、预算，不发送全量购物画像 |
| 复杂商品需要品牌团队的专业适配研究 | 经受控 Agent Gateway 委派外部专业 Agent | 先确认返回的是可核验产物，而非营销话术；品牌来源和商业倾向必须标注，价格库存仍回源 |
| 订单状态查询、优惠资格判断、创建订单或支付 | 确定性业务服务与独立交易状态机 | 不能靠多 Agent “商量”授权或订单状态；高风险动作不因专家建议就自动执行 |

低价值请求、不足以拆分的强串行任务、严格低延迟入口、相同数据同一问题的重复投票、无法限制权限或控制外部费用的任务，不启用多 Agent。无必要的跨部门协作可以通过已授权的 Domain API 完成。

#### 3.4 架构放在哪里：不是再建一个全局大脑

**App 仍拥有业务 Workflow。**根据场景选择确定性短链路、单 Agent 或受控多 Agent。search-runtime 和 rec-runtime 继续是独立的根任务承载池；不是把一次根请求同时交给两个池各跑一遍。

**主 Runtime 内增加 Delegation Manager（委派管理器）。**它与 Tool Adapter 同属执行机制，处理受控的 delegateTask 动作：校验目标 Agent、任务边界、身份和可委派权限，创建 childRun / remoteTask 映射，预留预算、限制并发与深度、追踪状态、收集产物、取消和回收。可先做库或进程内模块；不要求新增一个网络中心服务，也不是独立 LLM。

**内部子 Agent 使用相同底座、不同任务上下文。**由受控 Worker 执行自己的小循环，按本任务白名单调用模型、Tool、Domain 和 RAG。共享的是基础服务与受控引用，不是可任意修改的全局 Messages。主任务上下文默认只读投影；childRun 使用独立 Memory / 检查点命名空间。子 Agent 不直接覆盖用户长期偏好、总预算或主任务候选集，产物必须由主任务验证合并。

**Agent Gateway 管理外部 Agent 的运行边界。**包括经审核的 Agent Registry / Agent Card、协议与版本适配、OAuth / mTLS 等服务鉴权、最小字段投影、外部任务映射、超时与有限重试、查询状态、取消、产物验证、出口审计。内部受控 Agent 可使用现有 RPC；跨平台长期任务按互操作需求采用 A2A 或明确约定的 HTTPS task API，不强制全面迁移。MCP 侧重 Tool / 资源接入；A2A 描述 Agent 任务协作；Skill、MCP、A2A 不是彼此替代的同一层概念。〔M2、M3、M4〕

**agentControl 增加委派治理，但仍不进入逐请求链路。**管理 Agent 目录、Owner、能力与 I/O schema、Skill / Prompt / 模型版本、可委派矩阵、数据出口字段、read/write 风险等级、最大深度、预算、SLA、能力契约测试和灰度回滚。Runtime / Gateway 消费已生效快照并做在线策略执行，权限撤销及时失效。外部 Agent Card 是能力声明，不是可信证明，更不是授予账户权限的凭证。〔M3〕

部署口径同步扩展：原“6 个逻辑服务、7 个部署单元”仅是核心基线，不包含可选 Agent Worker 池或外部 Agent Gateway。子 Agent 起步可复用本池 Worker；外部 Agent 由对方独立部署。是否拆分服务由资源隔离、SLA、风险和发布需求决定。

#### 3.5 新增调用关系：委派是子任务，不是无边界转发

| 调用方 → 被调用方 | 传递什么 | 返回 / 控制边界 |
| --- | --- | --- |
| 主 Agent → 本池 Delegation Manager | goal、输入引用、验收条件、所需能力；目标限于允许目录 | 模型只能提出委派，身份、权限与预算由服务端决定 |
| Delegation Manager → 内部 Agent Worker | rootRunId、parentRunId、childRunId、任务快照、子预算、deadline | 子 Agent 可有自己的 LLM / Tool 循环；不能另起用户总任务或绕过父任务控制 |
| 子 Agent → 模型服务 / Tool Adapter → Domain / RAG | 专用 Prompt、最小上下文和已授权 schema | 延用同一工具治理；执行费用计入根任务，子任务用独立状态空间 |
| Delegation Manager → Agent Gateway → 外部 Agent | allowlisted agentId / endpoint、请求 ID、必要数据、约定任务契约 | 映射 remoteTaskId，支持协商的进度 / 查询 / 取消；不透传主用户凭证和完整画像 |
| 内 / 外部 Agent → 委派管理器 → 主 Runtime | 状态、产物、证据、限制、错误、用量及来源版本 | 这是返回产物，不是调用另一个根 Runtime；父任务验证后才能入主上下文 |
| 主 Runtime → Memory / Reply / 权威业务服务 | 合并后的候选、约束、证据与确认过的状态 | 唯一对用户交付者；核价与交易确认仍由权威系统完成 |
| agentControl → 配置 / 制品平台 → Runtime / Gateway / Worker | 可委派矩阵、版本、出口字段、配额与熔断策略 | 事前发布，权限实时约束；不让外部 Agent 自报权限后自动注册为可信执行方 |

**“一个任务一个主循环”需要精确表述为：一个 rootRun 只有一个根 Owner 和最终交付者；每个 childRun 可以有一个局部循环，但其权限、费用、深度和截止时间受到父任务约束。**两个根 Runtime 池不得递归互启根请求；允许通过统一委派契约调用注册的内部 Worker 或跨团队 Agent，并返回产物。不要把“禁止根任务递归”误读成“禁止任何跨服务 Agent 协作”。

#### 3.6 最小任务契约与运行保障

**示意输入契约（平台内部字段，并非 A2A 原样字段）：**rootRunId / parentRunId / childRunId、agentId / version、goal、acceptanceCriteria、inputRefs、scopeProjection、deadline、tokenAndCostBudget、maxToolCalls、maxDepth、requestKey、requiredOrOptional。身份与 scope 由服务端填写，不允许模型自填授权。

**示意产物契约：**taskId、status、artifacts、candidateRefs、evidenceRefs、limitations、sourceAndVersion、usage、error。状态至少区分运行中、等待补充 / 授权、完成、失败、取消与结果未知；外部状态按协商协议映射，不把我方超时误标为对方失败。completed 只代表对方报告完成，仍需校验业务与证据。外部 Agent 无法提供可信用量或费用上限时，应限制预付费 / 请求次数或禁用该路由，而不是假定成本为零。〔M4〕

- **预算守恒与深度限制：**主任务先预留子预算，主模型、全部内 / 外部分支和汇总共用总额，不能给每个分支复制一份全局额度。起步默认一层子任务、禁止子 Agent 再委派；具体并发数、成本阈值通过压测和收益实验确定，非行业通用常数。
- **状态与恢复：**持久记录委派账本和 requestKey → remoteTaskId；恢复先查既有任务，避免宕机后重新启动重复任务。内部 Worker 用租约 / fencing 等机制防止双执行；外部系统是否支持幂等与查询必须先做契约测试，不承诺跨系统 exactly-once。
- **取消与未知结果：**父任务取消后停止新派发，向存量子任务发送取消并记录确认；外部不支持或未确认时标记“取消待确认 / 状态未知”，停止采纳迟到结果并继续按策略查状态。取消不是业务回滚，已经发生的写动作不能被 Agent 状态抹掉。
- **数据边界：**外部只收到任务必要字段、短期且受众限定的授权引用；不发送全量 Memory、密钥或内部持久 URL。返回产物也可能包含恶意指令或不可信链接，需安全处理、来源核验和受控读取，不自动执行其建议工具。
- **结果合并：**按稳定 SKU / 任务版本去重，保留支持与反证、来源时间和限制。总预算、套装兼容性与可售性由主任务及业务域最终校验，不能简单拼接三个专家答案或平均未经校准的评分。
- **等待用户与恢复：**子任务的澄清 / 授权请求上收主 App 展示；不让外部 Agent 绕过 App 索取密码、支付或扩权。用户回复后按协议继续或创建后继任务；对已终结的远程任务不盲目“重启”。〔M4〕
- **写操作与交易：**首期所有委派仅只读；若未来开放副作用，必须单独评估权限、可信确认、幂等与审计。用户认可推荐不是下单授权，外部 Agent 的成功文本不是权威订单状态。
- **故障与可观测：**每个子任务记录父子 Trace、Agent / Skill / Prompt / 模型 / 数据版本、成本与产物引用；可选分支超时可降级，必需证据缺失则收窄或拒绝结论，不能装作全部研究完成。

#### 3.7 把“高性价比选购”升级为多 Agent 的例子

前文 500 元耳机案例默认仍走单 Agent。只有当用户提出“几款耳机的测评互相矛盾，请深入核实长期使用与安卓适配，比较花更多的钱是否值得”，并且材料规模与实验收益确实支持时，主 Agent 才考虑受控委派。

1. **主任务先确定候选与硬约束。**用普通 searchProducts / getProductFacts 获取有效 SKU、预算和当前价格；这些确定性查询不必包装成子 Agent。
2. **证据研究子 Agent A**：独立研究同型号说明、可信测评和评价差异，返回支持、反证、引用及适用条件。
3. **适配与使用成本子 Agent B（按需）**：研究安卓功能限制、耗材、保修与长期使用限制；只有需要多步查证时才启动。A、B 在共享只读候选快照后可并行，各自不改总预算。
4. **外部专业 Agent C（可选）**：若其他团队已有本平台缺少的专业评测 / 适配研究能力，经审核的 Agent Gateway 委派；无必要或无可核验来源就不调用。品牌自述必须标注，不能作为独立测评。
5. **主任务验证合并与回源。**读取各分支证据，处理冲突、重新核价，给出“更省钱且够用 / 加价获得的实际收益 / 证据不足”的比较。C 超时不影响已有可靠事实，但不能声称已完成 C 的研究。

这不是固定要求每次调用 A、B、C。若简单并行 Tool 已能得到同样质量的结果，应保留单 Agent，省掉额外模型轮次、等待与上下文转交成本。

#### 3.8 团队分工与实施顺序

| 团队 / Owner | 负责范围 | 与其他团队的协作契约 |
| --- | --- | --- |
| 搜索 / 推荐应用团队 | 根任务产品体验、启用策略、主 Skill、结果验收、降级与实验 | 对总任务成功与用户交付负责；不把质量责任全部交给子团队 |
| Agent 平台 / Runtime 团队 | 委派管理器、Worker 执行协议、父子预算、状态恢复、任务事件 | 统一 SDK 与契约测试，支持独立部署和灰度；共建机制，不统一所有场景策略 |
| 专业子 Agent 团队 | 专业 Skill、允许工具、产物 schema、证据质量与领域评测 | 提供明确 I/O、版本与限制，不直接修改主用户状态 |
| 外部 Agent 所属部门 / 合作方 | 对方 Agent 的运行、鉴权、任务接口、SLA、取消与用量机制 | 联合测试超时、恢复、重复请求、权限撤销、产物撤回和版本升级；明确值班联系人 |
| 安全 / 模型 / 数据平台 | 最小授权、出网审批、模型配额、知识 ACL、Memory 隔离与删除 | 权限与预算不能仅在 Prompt 中约定；外部数据去向和用途可审计 |
| 测试 / 评测 / SRE | 故障注入、召回与证据验收、P95 与成本、监控告警、容量和回滚 | 主任务与子任务分层定位，并对整棵任务树演练取消和恢复 |

实施顺序：先保留单 Agent / 并行工具基线 → 验证一个只读内部子 Agent 场景 → 上线有界委派、状态隔离和汇总 → 经收益与安全门禁后接入一个外部 Agent → 再评估更深层协作。暂不建设自由互聊的 Agent 群、不开放任意发现与无限递归、不把 MCP 接入数量当作多 Agent 成熟度。

#### 3.9 官方参考与适用边界

- 〔M1〕Anthropic，How we built our multi-agent research system，2025-06-13：https://www.anthropic.com/engineering/multi-agent-research-system 。公开的是研究任务中的主 Agent / 子 Agent 模式、并行探索与成本挑战，不是本项目性能承诺。
- 〔M2〕LangChain，Subagents：https://docs.langchain.com/oss/python/langchain/multi-agent/subagents 。主 Agent 通过工具式接口调用专业子 Agent、隔离上下文；简单少工具场景建议用单 Agent。
